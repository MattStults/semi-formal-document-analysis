# l1_170_n056 — translation notes

Span (narrowed, verbatim):

> "Models should honor user requests unless they conflict with developer-, system-, or
> root-level instructions."

---

## 1. Span enumeration — written BEFORE reading the review list, schema or examples

**Obligations / prohibitions / permissions / preferences**

| # | force | bearer | act | triggering condition | wording |
|---|---|---|---|---|---|
| N1 | defeasible obligation ("should") | *Models* — the assistant | honor a user request | there is a user request | "Models **should honor** user requests" |
| N2 | defeater on N1 (not itself a norm) | — | — | the request "conflict[s] with developer-, system-, or root-level instructions" | "**unless** they conflict with…" |

Nothing else. No permission is granted, no prohibition is stated, no comparative
("more X than Y", "minimize", "prefer") appears.

**Structural / descriptive facts**

* F1 — there exist instructions at levels named *developer*, *system* and *root*
  ("developer-, system-, or root-level instructions"). The span presupposes these
  levels; it does not define them.
* F2 — a user request can stand in a *conflict* relation with such an instruction
  ("they conflict with"). The span presupposes that relation; it does not say what
  makes a conflict.

**What the span does NOT state** — the load-bearing list

* ⛔ It does **not** say what to do with a request that DOES conflict. It withdraws
  the obligation; it does not forbid honoring, does not oblige refusing, does not
  oblige following the higher instruction instead. "unless" removes a requirement;
  it does not install its opposite.
* ⛔ It does **not** state the ranking root > system > developer > user. It names
  three levels; the *ordering* is another node's content (`authority_levels_hierarchy`
  arrives in `NEEDS`, i.e. the graph itself says this node does not establish it).
* ⛔ It does **not** mention the guideline level or the no-authority level.
* ⛔ It does **not** define "honor", "request" or "conflict".
* ⛔ It does **not** say the obligation is absolute — "should", not "must".
* ⛔ It says nothing about *who* wins a conflict between two higher-level
  instructions.

## 2. Review-list findings — every entry, including the ones that found nothing

**P1 — polarity of a `prefer`.** *Nothing found: the module emits no `prefer`.* Checked
whether "should honor" is a comparative that ought to be `prefer`: it is not. The
schema's test is that "no situation violates" a preference; a model that ignores a
non-conflicting user request plainly violates this span, so `prefer` would delete the
violation condition. `oblige` is right, and the act named (`honor_request`) is the act
the span wants MORE of, so no polarity inversion is possible.

**P2 — deontic force on a non-norm.** *Nothing found.* The subject of the main verb is
"**Models**" — the bearer is the assistant, so `asserts` (not `ontology`) is the right
home for N1. The two facts F1/F2 are *not* rendered deontically; they live in
`ontology`/`inputs`.

**P3 — dropped obligation with the exception retained. ⚠️ THIS ENTRY WAS MEASURED ON
THIS EXACT CLAUSE, and it is the failure this module exists to avoid.** The recorded
production failure emitted only `forbid honor_request` on conflict and let "should
honor" survive nowhere but in `claims` C1. Applied as instructed — each `claims` entry
checked against the asserts:

* C1 "the model should honor a user request" → encoded, `asserts(…, oblige,
  honor_request(Q)) :- user_request(Q), …`.
* C2 "that obligation lapses where the request conflicts…" → encoded, as the
  `not higher_authority_conflict(Q)` conjunct of the SAME rule.

No claim is encoded nowhere. Note the direction of the fix: the exception is a
*condition on the obligation*, not a second rule — writing it as a second rule is what
tempts a translator to write the second rule and forget the first.

**P4 — disjunction encoded as conjunction.** *Found and handled.* The span's "or" is in
"developer-, system-, **or** root-level instructions" — a disjunction over the level of
the *defeating* instruction, not over acts. It is encoded once, as a single condition
that any one of those levels satisfies (`authority_levels_hierarchy(L, user_authority)`
holds for L = developer, system or root independently). There is exactly one `oblige`,
so no shared body carries several obliges.

**P5 — scope drift, both directions.** Checked both:
*Too wide?* The obligation fires only on `user_request(Q)` — the span's subject is "user
requests", so it does not reach developer or system requests. The defeater fires only on
levels ranked above the user level, so it does not reach guideline-level conflicts,
which the span does not mention.
*Too narrow, in the dangerous direction?* The obligation is the permissive-side rule
here, so narrowing it is the safe direction; I did not narrow it anyway. The warning
about "a body added to encode 'regardless of context' WEAKENS the rule" does not apply:
no context body was added.

**P6 — content sourced outside the narrowing.** *Checked; the question does not arise.*
The `[node narrows this span to: …]` string is **byte-identical** to the printed
`L0093-L0093` line and to `ESTABLISHES` (verified programmatically). Every asserted
predicate traces to the narrowed sentence. **The contract question therefore does not
fire on this clause, and I have deliberately NOT created `PROVISIONAL.md`** — a ruling
written on a clause that does not exercise it would be a ruling made on no facts.

**P7 — defeasibility must be encoded or recorded.** *Found; encoded, not merely
recorded.* The span hedges twice: "**should**" and "**unless**".
— "unless" is encoded as the body conjunct `not higher_authority_conflict(Q)`.
— "should" (as against "must") is **NOT encodable**: `status` has one obligation pole,
and the schema reserves `toggleable` for `world` facts. So it is recorded here: this
module's `oblige` is byte-identical to what a "must honor" span would produce, and
nothing in the artifact distinguishes them. That is a real residual loss and it is
stated rather than papered over. (I considered downgrading to `prefer` to mark the
softness; rejected under P1's own test — see P1 above.)

**P8 — tautology.** *Nothing found.* No head appears in its own body:
`honor_request(Q)`'s body mentions `user_request` and `higher_authority_conflict`;
`higher_authority_conflict(Q)`'s body mentions neither itself nor anything glossed as
itself. No gloss restates its predicate name — checked by hand against the schema's own
word-subset test, and the validator's restates-name check passed on all five glossed
borrows.

**P9 — declared and never used.** *One finding, deliberate.* Every declared name appears
in a body: `user_request/1`, `conflicts_with/2`, `instruction_at_level/2`,
`authority_levels_hierarchy/2` and `higher_authority_conflict/1` all appear as
literals; `user_authority/0` appears as the **second argument** of
`authority_levels_hierarchy(L, user_authority)` rather than as a literal of its own —
which is the `defaults_level/0` pattern the worked example uses verbatim. So nothing is
dead. This was the reason to prefer the hierarchy encoding over the literal one (see §3).

**P10 — both poles of a GOOD/BAD example.** *Not applicable: the span is not an example
pair.* Checked and confirmed — no "Good"/"Bad" arms, no dialog.

**Anti-rules.** (a) No `forbid X(R) :- X(R)` binder is present, so nothing to leave
alone there. (b) The two `requires-unprovided` notes DID fire (both NEEDS names) and I
left them alone — the anti-rule says they fire on every correct single-clause module and
that moving the predicate to `inputs` to clear them destroys the distinction. (c) Status
and read-back were written independently and agree; I did not rewrite the read-back to
make them agree.

## 3. Decisions, each with its decisive wording

**D1 — `oblige`, not `prefer` or `forbid`.** Decisive wording: "Models **should honor**
user requests". A directive with a bearer and an act, not a comparative. `prefer` is
defined as attaching a preference no situation violates; ignoring a compliant user
request violates this. `forbid` would need an act to prohibit and the span prohibits
nothing.

**D2 — ONE assert, not two. No `forbid` on the conflict branch.** Decisive wording:
"**unless** they conflict with…". "Unless" withdraws the requirement; the span never
says a conflicting request may not be honored, nor that the higher instruction must be
followed. Under the standing instruction to assert LESS where the span is silent, the
conflict branch is left unstated: the module says nothing about honoring a conflicting
request, and the `unclear` closure says so out loud. **Rejected by name:** adding
`forbid honor_request(Q) :- higher_authority_conflict(Q)`. That is the true content of
the surrounding section, but it is not the content of this sentence, and it is exactly
the over-assertion that is indistinguishable from a real rule once rendered.

**D3 — the defeater is a body conjunct of the obligation, not a separate rule.**
Decisive wording: the single sentence structure "should honor … **unless** …" — one
norm with one exception, not two norms. This is the direct fix for P3: encoded as one
rule, the obligation cannot be deleted while the exception survives.

**D4 — negation-as-failure (`not higher_authority_conflict(Q)`) rather than a positive
`no_conflict/1` input.** The `Assertion` docstring warns against "deriving a verdict from
the mere ABSENCE of something". That warning bites where the *grounds* are absent; here
the defeater is fully DERIVED inside this module from positive facts
(`conflicts_with`, `instruction_at_level`, the hierarchy), so the program can say
exactly why the obligation did or did not hold. A primitive `no_conflict/1` supplied
with the case would have hidden the three-part structure of "conflict with a
higher-level instruction" behind one opaque input, and P9 would then have found the
conflict machinery dead. `[RAN]` under clingo 5.x with two test requests: the
non-conflicting one derives the obligation, the conflicting one derives nothing.

**D5 — "developer-, system-, or root-level" encoded via
`authority_levels_hierarchy(L, user_authority)` rather than by naming the three
levels.** Decisive wording: "developer-, system-, or root-level instructions" — and the
node's own `NEEDS` gloss, "root > system > developer > user > guideline > no authority".
The levels above the user level are *exactly* developer, system and root, so the two
encodings have the same extension; this one uses both borrowed names as the graph
intends and keeps the module to one ontology entry instead of three.
**Rejected by name:** three ontology entries over `developer_level/0`, `system_level/0`,
`root_level/0`. It is more literal, but it needs four extra concepts, leaves
`authority_levels_hierarchy/2` dead, and states the same class.
⚠️ **The cost is recorded:** this rule now tracks whatever the hierarchy node says. If
that node ever ranked some fourth level above the user, this rule would silently follow
it past the three the sentence names. The ontology entry is licensed `assumed` with that
step named, so it is visible rather than buried.

**D6 — argument order of `authority_levels_hierarchy/2` is (higher, lower). UNSURE.**
The `NEEDS` gloss does not state an order. I followed the worked example's
`authority_levels_hierarchy(L, defaults_level)` = "L is above the defaults level", and
wrote the order into the concept gloss so that a mismatch with the provider node is
*visible* as a description disagreement rather than a silent inversion. If the provider
node turns out to mean (lower, higher), this rule fires on guideline-level conflicts and
not on root-level ones — the inversion is total, and the gloss is the only place it can
be caught.

**D7 — `user_authority` at arity 0.** The name is handed as "The user level of
instruction authority" — a *level*, i.e. a thing the hierarchy relates, not a property.
Arity 0 makes it the constant standing for that level, mirroring `defaults_level/0`.

**D8 — closure `unclear`, not `cepa`.** Follows directly from D2: having withdrawn its
obligation for conflicting requests, the span states nothing about them, so it does not
settle whether its silence permits or prohibits. `cepa` would have been the comfortable
choice and would have quietly turned "the span is silent" into "the span permits".

**D9 — `beats` empty.** Tempting reading: this sentence ranks higher-level instructions
over user requests. Rejected — `beats` relates CLAUSE ids and records who says so, and
this span names no clause; further, it does not say the higher instruction *wins*, only
that the model's obligation lapses.

**D10 — `forbid_body` empty.** The span says "should … unless", not "never". No claim
about the shape of the rule set.

**D11 — `user_request/1`, `instruction_at_level/2`, `conflicts_with/2` in `inputs`, not
`requires`.** The node's `NEEDS` block lists exactly two names; per contract 3 and the
heading-node example, everything else I identify is case-side. Which requests exist,
what level an instruction came from, and which pairs conflict are facts about the
conversation being judged.
