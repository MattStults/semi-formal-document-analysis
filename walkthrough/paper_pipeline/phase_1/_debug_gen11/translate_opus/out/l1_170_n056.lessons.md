# Lessons from `l1_170_n056`

Four candidate REVIEW_LIST entries. Each is phrased as a mechanical question a later
translator can run without knowing this clause. Each names what is NOT already covered
by P1–P10, because an entry that duplicates one is worse than none.

---

## L1 — the excepted branch is a HOLE, not a rule (the mirror of P3)

P3 catches *obligation dropped, exception kept*. This clause tempts the exact opposite
error just as hard, and P3 does not catch it: having correctly kept `oblige honor`, a
translator naturally adds a second rule `forbid honor_request(Q) :- conflict(Q)` to
"finish the sentence". The span never says that. Both errors come from the same
misreading — that "unless" names a second rule — and the review list currently sees only
one of them.

**Ask:** for every `unless` / `except` / `other than` in the span, list the asserts whose
body IS that exception condition. For each, quote the span words that state what may or
must be done in that branch. If you cannot quote them, the span withdraws a requirement
and installs nothing — delete the assert and let the branch be silent.

Fingerprint: an assert whose read-back is the *negation* of the module's other
read-back, with no span sentence behind it.

## L2 — a `cepa` closure re-asserts the silence you just declined to assert

New territory: nothing in P1–P10 mentions `closure` at all, and it is the one required
field that states a commitment with no textual anchor of its own. Having decided under
L1 not to encode the excepted branch because the span is silent, the natural closure to
write is `cepa` ("silence permits") — which says the very thing you just refused to say,
in the field whose whole purpose is that the choice would otherwise be invisible.

**Ask:** for each act class, name the branch of the span you left unencoded. Does your
closure value make a commitment about that branch? If your grounds for leaving it
unencoded were "the span does not settle this", then the only closure consistent with
those grounds is `unclear`. `cepa` and `cnpa` each need their own quotable wording.

## L3 — a borrowed relation of arity ≥ 2 has an argument ORDER the NEEDS gloss does not fix

`authority_levels_hierarchy` arrived glossed as *"the ranking of instruction authority
levels: root > system > developer > user > …"*. That fixes the ranking and says nothing
about whether the predicate is written (higher, lower) or (lower, higher). Guess wrong
and the rule fires on exactly the complement of the intended set — a total inversion
that every deterministic check passes, because arity matches, the name matches, and the
program is safe. `[RAN]` here: with the order flipped, this module's obligation would
lapse on *guideline*-level conflicts and hold on *root*-level ones.

**Ask:** for every `requires` / `inputs` predicate of arity ≥ 2, does the gloss you were
handed fix which argument is which? If not, write the order you assumed INTO your own
`concepts` gloss in words ("the first level ranks above the second"). The gloss is the
only channel in which the provider node's disagreement can ever surface; a bare
positional guess is unfalsifiable.

## L4 — a derived class quietly outsources the span's own enumeration to another node

The span enumerates: *"developer-, system-, or root-level"*. Encoding that as "any level
the hierarchy ranks above the user level" is extensionally identical **today** and is
the better module — it uses the borrowed vocabulary and costs one entry instead of four.
But its extension is now set by a different node, and if that node ever ranks a fourth
level above the user, this rule covers a level this sentence does not name. That is a
scope drift P5 cannot see, because it is not in the body as written — it arrives later,
through the link.

**Ask:** did you replace a list the span spells out with a class derived from borrowed
vocabulary? If yes: would an edit to the OTHER node change which things this rule
reaches? If yes, the entry is not `textual` — mark it `assumed` and name that step, so
the dependency is on the record rather than in your head.
