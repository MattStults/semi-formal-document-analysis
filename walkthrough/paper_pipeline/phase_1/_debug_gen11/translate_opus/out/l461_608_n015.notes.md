## 4. Decisions, each with its decisive wording

**D1 — `ontology`, not `asserts`.** Decisive wording: *"Examples of side effects **include**:"*
The main verb's subject is a part of the document. P2's rule: not the assistant → fact.
Rejected by name: eight `forbid`/`prefer` entries over `send_email(A)`, `delete_file(F)` and
so on. The document nowhere prohibits sending an email; a module that did would state a rule
the Model Spec does not have, and — worse for this section — would contradict the
surrounding text, which assumes the assistant *does* take these actions within scope.

**D2 — `ontology`, not `defines`.** Considered seriously, because `defines(Clause, Kind, Term)`
does "bring a term under a class" and `defines(l461_608_n015, side_effect, sending_email)`
reads well. Rejected on the decisive word *"**include**"*: `Definition`'s contract is that it
*"fixes the extension that other clauses quantify over"*, and a list introduced as
non-exhaustive fixes no extension. Second, independent ground: `defines` has no slot for the
`PROVIDES` name, so nothing named `side_effect_examples` would be derivable and every node
waiting on this one would be stranded.

**D3 — one predicate, `side_effect_examples/1`, and no `side_effect/1`.** The `PROVIDES`
block says *"use EXACTLY these names as the predicates this module defines"* and names one.
`side_effect/1` is not in `PROVIDES` and not in `NEEDS`, so this module neither owns it nor
borrows it. This is also the under-assertion: "listed as an example of a side effect" is
strictly weaker than "is a side effect", it is what the span literally says, and it stays
visible and citable.

**D4 — eight atoms, one per bullet.** Decisive: the span is eight list items. Nine atoms
would invent a list item; seven would drop one.

**D5 — the item-5 constant is `tool_request_containing_sensitive_user_data_including_web_get`.**
Decisive wording: *"Making tool requests (**including** web GET requests) that contain
sensitive user data"*. *"including"* is an explicit statement of coverage, not an
illustration — it exists to say that a read-only request counts, which is the least obvious
thing in the list and the one a reader would most plausibly assume excluded. Rejected by
name: **(a)** a ninth atom `side_effect_examples(web_get_request_containing_sensitive_user_data)`
— rejected because it manufactures a list item the document does not have (D4); **(b)**
`tool_request_containing_sensitive_user_data`, dropping the inclusion — rejected because
constants carry no gloss field, so the constant name is the *only* place that content can
live in this module, and the drop would be invisible. The name is long on purpose.

**D6 — the two `(e.g., …)` parentheticals are not separately encoded.** Decisive:
*"e.g."* marks an illustration of an item already stated generally, where *"including"*
(D5) marks coverage a reader might doubt. `ticket purchases` is already inside
`direct_expenditure`; `POST requests` is already inside `modifying_external_document`.
Encoding them would be padding, and would raise the same invented-list-item problem as D5(a).
Both survive in `claims` C2 and C5.

**D7 — C10 (the sub-agent recursion remark) is recorded and not encoded.** Decisive
wording: *"(which **may** itself incur further side effects)"*. It is a modal possibility
claim about consequences, and the only predicate it could be written with is not in
`PROVIDES`. ASP has no possibility operator, so any encoding — `incurs_further_side_effects(delegating_to_sub_agent)`
— would flip *may* into *does*, an over-assertion indistinguishable from a rule. Left in
`claims` so it is visible that it was seen and declined, which is what P3 asks for.

**D8 — `claims` records the span, not the encoding.** C1 and C10 are in `claims` and in no
rule. This trips P3's *detector* by design; §2 accounts for both, and the schema's own words
for the field are *"the clause's distinct claims"*.

**D9 — `acts: []`, therefore `closure: []`.** Decisive: the span attaches no status to
anything, so the module governs no act class. `10_output_format.md`: *"A clause governing no
acts — a pure definition — needs no closure entry."* ⚠️ Note the near-miss: the eight
constants **name** act-kinds (sending an email, deleting a file). They are not `acts` — they
are the *subjects* of a classification, and putting them in `acts` would have forced eight
closure declarations, each of which is a commitment about what the document's silence means
for that act. This span settles none of them, so eight `unclear` entries would have been
noise and eight `cepa` entries would have been a fabricated permission.

**D10 — `root_authority/1`, arity 1.** NEEDS text: *"**Rules** in the #control_side_effects
section carry root authority"* — the bearer is a rule, so one argument. UNSURE only on the
arity convention (a `/2` relating rule to level is conceivable); `/1` asserts less, and the
NEEDS sentence names exactly one level.

**Deliberately left alone:** the `requires-unprovided` note (anti-rule 2); the repeated
per-atom `gloss` string, which the schema requires to describe the *predicate* rather than
the instance, so eight identical glosses is the contract working, not duplication; the
surrounding section's norms, which belong to other nodes.
