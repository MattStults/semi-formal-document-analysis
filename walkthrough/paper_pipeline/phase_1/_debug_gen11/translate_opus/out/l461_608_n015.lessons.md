# Lessons from `l461_608_n015` — candidates for REVIEW_LIST v2

Three entries. All three are about **enumeration nodes** — a node whose content is a bullet
list of examples — which is a shape the current list does not address anywhere. Each is
phrased as a question a later translator can apply mechanically. None duplicates P1–P10:
P6 and P7 are adjacent to L2 but ask about a different object (P6 about which *text* licenses
a predicate, P7 about pushing a defeater into a *body*; L2 is about the choice of predicate
*name* under closed-world negation).

---

## L1 — A ground constant is the only place its own qualifier can live, and nothing checks it

An `ontology` entry has a `gloss`, but the gloss is contractually about the **predicate**,
not the instance (`schema.py:OntologyFact`: *"one sentence saying what this PREDICATE means
— not what this particular instance of it asserts"*). So on a node whose entire content is a
list of ground facts, every distinction between the items lives in the **constant names** —
which have no gloss slot, no read-back, and no validator that looks at them. A qualifier
dropped from a constant name is dropped from the corpus, silently, behind a module that
passes every check.

Here: *"Making tool requests **(including web GET requests)** that contain sensitive user
data"*. Both halves are droppable. Drop *"that contain sensitive user data"* and the module
sweeps in every tool request; drop *"including web GET requests"* and it narrows to mutating
requests, losing the one non-obvious claim in the list.

**Ask:** for every ground constant you write, list the qualifiers the span attaches to that
item — restrictions (*"that contain…"*, *"on a user's computer"*) and explicit inclusions
(*"including…"*). Is each one present in the constant's name? If a qualifier is not in the
name, name where else in this module it survives. If the answer is nowhere, the name is
wrong, however long the correct one has to be.

## L2 — "include" is a hedge on the PREDICATE NAME, not on any body

P7 tells you to push a defeater into a body. An enumeration node offers no body to push it
into — the facts are ground — so the hedge has to be absorbed by what the predicate is
*named for*. The choice is between a predicate that means **listed as an example of X** and
one that means **is an X**, and under closed-world negation the two say different things
about everything *not* on the list: the first yields "not one of the listed examples" (true),
the second yields "not an X" (a claim *"Examples of side effects **include**"* explicitly
refuses to make).

**Ask:** does the span introduce its list with *include*, *such as*, *for example*, *among
others*? If so — (a) does your predicate name say list-membership rather than
class-membership, and (b) does its concept gloss state in words that the list is not the
whole class? If the node's `PROVIDES` already hands you a name of the first kind
(`side_effect_examples`), that is the graph telling you the answer; do not "improve" it into
the class name, and do not additionally define the class predicate, which `PROVIDES` did not
give you.

## L3 — Naming a kind of action does not make it an act, and treating it as one fabricates a closure

`acts` is not "action words that appear in the span". Every distinct functor in `acts` forces
a `closure` declaration — a commitment about what the document's **silence** means for that
act class — and a classification node settles no such thing. Here the eight constants all
name kinds of action (sending an email, deleting a file, delegating to a sub-agent), and the
pull toward `acts: ["send_email(A)", ...]` is strong. Eight `cepa` entries would have been
eight fabricated permissions; eight `unclear` entries would have been eight commitments the
node never makes.

**Ask:** for each action-shaped term in your module, is it the *subject* of a classification
("this act is of that kind") or the *object* of a status ("this act is forbidden/permitted")?
Only the second belongs in `acts`. And run the check backwards: for every entry you put in
`acts`, can you write its `closure` reason as a sentence **drawn from the span** — as
`Closure.reason` requires? If the reason has to be invented, the act probably does not belong
in `acts` either.
