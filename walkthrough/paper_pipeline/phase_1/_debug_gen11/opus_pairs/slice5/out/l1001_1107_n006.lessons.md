## C1 — Does `P9` exempt `PROVIDES` names as well as `NEEDS` names?  ⭐ highest value

**MEASURED, on this clause.** P9 was corrected once already because its original form fired
on every correct node module (the unused `NEEDS` name in `requires`). **The corrected form
still fires on a correct module, by a second route the correction did not cover.** P9-corrected
asks whether every name *you coined* — "anything in `ontology`" — appears in some body. A
`PROVIDES` name is delivered as an `ontology` entry and is a **document-side object other nodes
reference**, not a condition this node tests, so it legitimately appears in no body. Here
`privacy_protection_rule` is exactly that, and P9 as written flags it.

The exemption is not "any unused ontology atom is fine" — that would give back the dropped-
content detector P9 exists to be. It is narrow: **the name is in the node's own `PROVIDES`
block.**

**Ask:** for each unused name in `ontology`, is it a `PROVIDES` name? If yes, it is
contract-required (deliver what `PROVIDES` promises) and must be left alone. If no, P9 stands
and it is the fingerprint of dropped content.

⭐ **MECHANICALLY CHECKABLE — yes, a few lines.** Parse the `PROVIDES:` block from the node's
prompt into a name set; compute the set of ontology-atom functors appearing in no `body` and no
assert `body`; report the difference. Flag only names outside the `PROVIDES` set. The same
parse gives a second free check — see C2.

## C2 — Is every `PROVIDES` name actually DERIVABLE from this module?

**INFERRED** (this module complies, so the failure was not observed here — but the failure mode
is the mirror of the one the worked example names in prose: *"other nodes are waiting on this
module to make that predicate derivable, and abstaining would strand every one of them"*). The
prose obligation exists; **no review-list entry turns it into a check**, and nothing in the
schema enforces it — a module can mention its `PROVIDES` name in `concepts` only, pass every
breach check with zero findings, and strand every consumer. A `concepts` entry declares a
meaning and derives nothing.

**Ask:** for each name in `PROVIDES`, does it head an `ontology` entry (or an `asserts`/
`defines` entry)? A `concepts` entry alone does **not** satisfy it.

⭐ **MECHANICALLY CHECKABLE — yes, and this one is exact, not heuristic.** For each
`PROVIDES` name `n`: assert `n ∈ {atom.split("(")[0] for atom in module.ontology}`. Three
lines given the prompt parse from C1. Worth running corpus-wide as a coordinator sweep, since
it is a *silent* failure that produces a stranded link rather than an error.

## C3 — N8 at arity 1: is the argument's TYPE stated, not just its order?

**MEASURED, and the disagreement is live in the corpus right now.** N8 is scoped to relations
of arity ≥ 2, where the hazard is argument *order*. The identical silent failure exists at
**arity 1** as argument *type*. This node's `NEEDS` gloss for `root_authority` reads *"rules in
the #protect_privacy section carry root authority"* → the argument is a **rule**. The sibling
node `l1001_1107_n005`, which is the node that **provides** the name, emitted
`root_authority(protect_privacy)` → the argument is a **section**. Both are fluent, both pass
every deterministic check, and they link cleanly and are wrong (failure mode #9). N8's trigger
condition — arity ≥ 2 — does not fire on either.

**Ask:** for each borrowed relation of arity **1**, what kind of thing is its argument — a
document object (section, heading, rule) or a situation object? Is that stated in your
`concepts` gloss in words a mismatching provider would visibly contradict?

⭐ **MECHANICALLY CHECKABLE — partly, and the partial check is the valuable half.** The gloss
wording cannot be judged mechanically, but the *disagreement* can: across all modules, group
`concepts` entries by name, and flag any name where one module's ontology instantiates it with
a ground constant and another module's gloss describes a different kind of argument — or, far
cheaper and fully exact, flag any name where one module's ground instance is a document
constant while another module's use of it sits in a body alongside situation predicates. Even
the crudest version — *"name declared in ≥ 2 modules with ≥ 2 distinct glosses"* — surfaces
this pair.

## C4 — Where does the concessive live? (and: is at least one assert free of it?)

**MEASURED as a near-miss on this clause** — the first shape I considered for *"even if the
information is available somewhere online"* was a body literal, which P5's ⚠️ then caught. The
list already has the two halves separately: P5 warns that a body added for "regardless of
context" **weakens** the rule, and N6 sends the exclusion to `forbid_body`. **Neither states
the residual check**, which is what a later reader can actually apply to a finished module:
after the remedy, does an unconditioned rule still exist?

This matters because the remedy has a plausible wrong form: writing the *single* assert with
the concessive predicate in its body **and** adding the `forbid_body` ban. That module has N6's
required entry, reads correctly, and still fires only where the information is online.

**Ask:** if the span contains a concessive (`even if`, `even when`, `regardless of`, `whether
or not`), name the predicate the concessive introduces. Is there at least **one** assert whose
body does not contain it?

⭐ **MECHANICALLY CHECKABLE — yes, and cheaply, keyed off `forbid_body`.** For each entry in
`forbid_body`, take `banned` as the concessive predicate `b`; assert
`any(b not in (a.body or "") for a in module.asserts)`. Zero-config, no NLP: `forbid_body`
already names the predicate, so the check needs nothing from the span. It fires exactly on the
wrong-form remedy above.

## C5 — Is the excluded text of the narrowing PERMISSIVE or RESTRICTIVE, and did the closure move accordingly?

**INFERRED** (my `closure` deliberation on this clause, §4.2 of the notes — reasoned, not
measured to fail). P6 tells you not to *encode* content outside the narrowing. It does not tell
you that the excluded content still bears on **one** field: `closure` is a claim about what the
document's silence means, and the narrowing manufactures a silence the document does not have.
Here the excluded sentence (*"For public figures, the assistant should be able to provide
information that is generally public…"*) is **permissive**, so `cepa` agrees with it and the
`cepa`/`unclear` choice is safe either way. Had the excluded sentence been **restrictive**, a
`cepa` closure would have asserted a permission the document contradicts one sentence later —
and P6 would have been satisfied throughout, because nothing was encoded from it.

**Ask:** does the text outside the `[node narrows this span to: …]` bracket permit or restrict
the same act class you are declaring closure on? If it restricts, justify `cepa` explicitly or
use `unclear`.

⭐ **MECHANICALLY CHECKABLE — no, not in a few lines.** It needs the polarity of a sentence
the module never encodes. Recording it as a *notes-discipline* entry rather than a checkable
one: the drafter must write the answer down in the closure deliberation. The only mechanical
half available is a flag, not a judgment — *"span was narrowed AND `closure` contains a
`cepa`"* → require a sentence in the notes naming the excluded text. Cheap, but it fires often,
so it belongs to the coordinator's review rather than to the drafter's checklist.
