## 4. JUDGEMENT CALLS AND UNSURES

### 4.1 `privacy_protection_rule` is nullary and appears in no body — deliberate

PROVIDES hands me the name with the gloss *"the rule that the assistant must not respond to
requests for private or sensitive information about people"*. That names **a rule**, singular
— a document-side object — not a class of situations. Two alternatives, both **rejected by
name**:

* **`privacy_protection_rule/1` over requests** (*"Q is a request falling under the privacy
  protection rule"*), which would make it a live classifier appearing in every assert body and
  would clear P9 automatically. Rejected: it silently redefines what the consuming node is
  asking for. A downstream node needing this name will be saying something *about the rule*
  (that it carries root authority, that some exception qualifies it), and a predicate over
  requests cannot receive that. Clearing a review-list ask by changing what the name means is
  the wrong trade.
* **`privacy_protection_rule/1` over rules, with a coined constant argument** (e.g.
  `privacy_protection_rule(no_response_to_private_info_requests)`). Rejected on N10: that
  constant traces to no substring of the narrowed text, and it buys nothing the nullary atom
  does not already give.

So the atom is nullary and unused in bodies. **The ground for leaving it alone is about the
span and the graph contract, not about the schema** — the rule is an object other nodes
reference, and its *content* is carried by the two asserts, so nothing is dropped. (I am
stating the ground in that form on purpose: `l1001_1107_n005`'s L8 records that a decline
whose ground is about the schema's options rather than about the document is the shape to
distrust. This one is about the document.)

**UNSURE (low):** whether the consumer wants `privacy_protection_rule` as a nullary atom or
as a constant it can pass as an argument. In ASP the two are the same symbol, so a consumer
writing `root_authority(privacy_protection_rule)` links cleanly either way. I do not think
this can bite, but I have not verified it against a consuming node.

### 4.2 `closure` on `respond_to` is `cepa`, and `unclear` was considered

`cepa` says: where this clause is silent about responding, responding is permitted. The
ground is in the clause — it bars responding **only** to requests for private or sensitive
information about people, and responding to anything else is the assistant's ordinary
business the clause says nothing against.

**`unclear` was the live alternative**, on the following worry: the narrowing cuts off the
public-figures sentence (X2), so this module is silent about a branch the surrounding document
actually speaks to, and N7 warns that a `cepa` closure can re-assert a silence you just
declined to assert. **Rejected**, for two reasons. First, N7's case is an *"unless"* arm —
a requirement the span itself withdraws — and this narrowed span withdraws nothing; it has no
excepted branch at all. Second, the direction is safe: X2 runs *permissive* (public-figure
information may be provided), so `cepa` agrees with the excluded text rather than contradicting
it. `cnpa` would have been the invention — it would forbid every response the document never
forbade.

### 4.3 `root_authority/1` — an N8 hazard one arity below N8's trigger  ⚠️ UNSURE

N8 is written for relations of arity ≥ 2, where the *order* of arguments can invert silently.
`root_authority` is arity 1, so the entry does not literally fire. **The same silent failure
is available anyway, as an argument TYPE ambiguity:** the NEEDS gloss handed to me reads
*"rules in the #protect_privacy section carry root authority"*, on which the argument is a
**rule**. It could equally have been read as *"the #protect_privacy section carries root
authority"*, on which the argument is a **section**.

These link cleanly to each other and are wrong — failure mode #9 exactly. I applied N8's
remedy at the lower arity: **my reading is written into the `concepts` gloss in so many
words** (*"the argument read here is the RULE that carries the authority, not the section that
confers it"*), so a provider disagreement surfaces as a description disagreement rather than a
silent type mismatch.

**I could not settle it, and it is worth the coordinator's attention.** The sibling node
`l1001_1107_n005` — same L-range, and it is the node that *provides* this name — emitted
`root_authority(protect_privacy)`, i.e. **the section reading**. That is the opposite of the
reading my own NEEDS gloss states. I deliberately did **not** change my gloss to match it:
rule 2 forbids guessing the content of a clause I was not shown, and my brief is to record
what *this* node has to assume. Recording the disagreement is the whole point of writing the
gloss down. But it is a real, live mismatch in the link set and it will not resolve itself.

never *testable*; assert 2 makes it testable without narrowing assert 1. If a reviewer wants

thing P5 protects.
