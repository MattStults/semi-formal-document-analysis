## C1 — Does the narrowed span carry an INLINE ATTRIBUTE BLOCK? Then "it is a heading" is not a ground to abstain.

**Ask:** does the narrowed text match `{#anchor key=value}` (a brace block containing an
`=`)? If yes, the span asserts a fact ABOUT THE DOCUMENT and the module must record it in
`ontology`; `outcome: "abstained"` is wrong however heading-like the rest of the line is.
If no, and the line is a bare `####` title, abstention is the likely correct answer.

**Why it needs saying:** `00_task.md` lists "it is a section heading" as the FIRST abstention
trigger, and my span is literally a `####` heading — the reflex answer is abstain, and it is
wrong. What separates the two heading cases is not the heading, it is whether the line
carries metadata. Nothing in the review list distinguishes them today, and the only thing
that saved this clause was a worked example that happens to cover the case.

**Tag: MEASURED** (on this clause; the negative arm — a bare title with no attribute block —
is INFERRED, I did not see one).
**⭐ MECHANICALLY CHECKABLE: yes, ~3 lines.**
`re.search(r"\{#\w+[^}]*=", narrowed) and module["outcome"] == "abstained"` → flag.
The converse arm is equally cheap: no brace-with-`=` in a `####` line and
`outcome == "translated"` with empty `ontology` → flag.

## C2 — Is the node's `PROVIDES` block non-empty while `outcome` is `abstained`?

**Ask:** does the node hand you a `PROVIDES` name? If so, abstaining leaves that name defined
by no module in the graph while other nodes carry it in their `requires` — a permanent
dangling edge that looks, downstream, exactly like a rule waiting on an unlinked clause
(failure mode ⑮). Abstention is still available, but only with the stranding written into
`abstain_reason` as an accepted cost.

**Why it needs saying:** abstention is ALL-OR-NOTHING by schema — `10_output_format.md`
requires every list empty — so there is no shape in which a module abstains on a passage's
norm and still delivers the predicate the graph is waiting on. The decision is therefore not
local to the span, and nothing in the current list says so.

**Tag: MEASURED** (the interlock is stated in `node_worked_example.md` and enforced by
`schema.py`; the abstention side was not exercised here — I translated).
**⭐ MECHANICALLY CHECKABLE: yes, ~4 lines**, and it needs no judgement at all:
parse `PROVIDES:` names out of the node's prompt text; flag when that list is non-empty and
`module["outcome"] == "abstained"`. Strictly a corpus-wide sweep, not a per-clause read.

## C3 — For each `concepts` entry marked `textual`, is its GLOSS content present in the narrowed span?

**Ask:** the contract rejects a gloss that restates its name, so every gloss must reach past
the name into what makes the predicate true. For each `textual` concept, check whether that
reaching content is in the narrowed span. If the gloss's substance comes from elsewhere in
the document (a shared definition, a section the node only points at), the entry is
`assumed`, not `textual` — the citation would otherwise stand behind content the cited text
does not carry.

**Why it needs saying:** the licence rules are written about FACTS, and the existing entries
police `ontology`/`asserts`. A `concepts` gloss is where the reviewer's whole understanding
of the predicate comes from, and it is the one place where the format contract actively
FORCES you past the span's words — so `textual` on a concept is systematically less
supported than `textual` on an ontology atom, and nothing currently notices.

**Tag: MEASURED** (this is the only content change any of my five turns made; the
`user_authority` concept went `textual` → `assumed` on exactly this test).
**⭐ MECHANICALLY CHECKABLE: partly, ~10 lines, as a SCREEN not a verdict.**
Content-word overlap: lowercase both, drop stopwords, and flag any `textual` concept whose
gloss shares fewer than ~2 content words with the narrowed span. It will over-fire on
legitimate paraphrase, so it is a "read this one" flag, not a failure. The judgement it
prompts is not automatable.

## C4 — Does a coined name match the forbidden per-section authority pattern?

**Ask:** for every name in `concepts`/`ontology`/`requires`/`inputs`, does it match
`<anything>_section_authority` or otherwise mint a section-local name for an authority
level? `authority_convention.md` forbids it by name: the concept belongs to the whole
document, and a section-local coinage stops the edge resolving to the shared definition.
Use the canonical `root_/system_/developer_/user_/guideline_authority` or
`authority_levels_hierarchy`, which the node hands you in `PROVIDES`/`NEEDS`.

**Ask, second half (the one that is easy to get wrong):** a section-named CONSTANT is not the
same violation. `avoid_abuse_heading/0` names a document heading and is an argument; it is
required by the encoding, not a coinage the convention bans. The pattern to flag is a
section name fused to an authority word in the PREDICATE position.

**Why it needs saying:** the convention is real, mandatory for every `authority=` heading
span, and lives in a file a translator only reads if told to. The review list does not
mention it, and the failure it prevents (~47% of one edge-divergence class) is invisible in
a single module.

**Tag: MEASURED** as a rule (`authority_convention.md` documents the ds3 coinages it was
written against); **INFERRED** that translators reproduce it when the file is not dispatched.
**⭐ MECHANICALLY CHECKABLE: yes, ~5 lines.**
Flag any declared predicate name matching
`r"_section_(root_|system_|developer_|user_|guideline_)?authority$"`, and separately flag
any name containing an authority level word that is NOT one of the six canonical names, for
a human to read. Constants used only as arguments are exempt — check the name in head
position, not every token.

## C5 — Does every coined predicate appear in a BODY, or only as a ground head?

**Ask:** P9 (corrected) asks whether every coined name appears in some body. Run it, then run
the case P9 does not name: a coined predicate that appears ONLY as a ground `ontology` head
and in no body is asserted and then never consulted — the module states a document fact that
nothing in the module, and nothing downstream that links to it by name, can use. Either give
it a use in the derivation it is supposed to license, or say in the notes why the bare
assertion is the deliverable.

**Why it needs saying:** N1 legitimises ground atoms for facts about the document, and P9's
"appears in some body" test reads naturally as satisfied by a head. The combination lets a
module assert a document fact that is inert — the very defect N1 measures, arriving through
the door N1 opened. Here the fix was one conjunct: `heading_authority(...)` is carried in the
`user_authority` body, so the derivation traces to the document's label rather than merely
sitting beside it.

**Tag: INFERRED.** I did not observe the inert form in a module; I observed that my own draft
was one edit away from it and that neither N1 nor corrected-P9 would have flagged it.
**⭐ MECHANICALLY CHECKABLE: yes, ~8 lines.**
Collect functors appearing in any `ontology[].body` / `asserts[].body`; for each ground
`ontology` entry (`body` is null), flag when its functor is in no body anywhere in the
module. Zero judgement, no false positives from the `NEEDS`-unused case (that lives in
`requires`, which this check does not touch).
