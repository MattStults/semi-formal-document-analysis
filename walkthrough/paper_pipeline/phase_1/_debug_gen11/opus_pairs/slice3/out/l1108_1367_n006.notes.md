# l1108_1367_n006 — translator notes

## (a) Stage 0 — span enumeration

NARROWED text (the only licence-bearing text):

> "The assistant must not generate hateful content targeting protected groups (race, religion,
> gender, sexual orientation, disability, etc.). This includes slurs, insults, and any language
> that demeans or dehumanizes."

**Finite verbs: 4.**
1. `must not generate` (sentence 1 — one finite modal+verb complex). *"targeting"* is a participle,
   not finite, so it does not add one.
2. `includes` (sentence 2, main verb)
3. `demeans` (sentence 2, relative clause)
4. `dehumanizes` (sentence 2, relative clause)

**Propositions `ESTABLISHES` demands: 2.**
1. the assistant must not generate hateful content targeting protected groups (with the
   characteristic list, ending in "etc.");
2. that class of content includes slurs, insults, and any language that demeans or dehumanizes.

**Mismatch? No.** 4 finite verbs against 2 propositions is not a scope conflict: verbs 2–4 all sit
inside proposition 2 — `includes` is the extension-fixing verb, and `demeans` / `dehumanizes` are the
two disjuncts of its last item. Nothing in the span is left over, and `ESTABLISHES` demands nothing
the span does not contain.

**Relation of sentence 2 to sentence 1 — decided and stated:** sentence 2 is an *extensional
expansion* of the object of sentence 1, **not a second norm**. Its subject is "This" (= the hateful
content the first sentence forbids), and its verb is `includes` — it widens what falls under the
already-stated prohibition rather than prohibiting anything itself. `ESTABLISHES` reads it the same
way (it subordinates the whole of it as "including …"). Encoding consequence: sentence 1 becomes the
single `forbid`, and sentence 2 becomes four `ontology` inclusion rules feeding that forbid's body
predicate `hateful_content/1`. Encoding sentence 2 as its own `asserts` entries would have asserted
four unconditional prohibitions on slurs/insults/demeaning/dehumanizing language *irrespective of
whether they target a protected group*, which is wider than the span.

## (e) Stage 5 reconciliation, and what I could not settle

**Every enumerated proposition is accounted for:**

* Proposition 1 (the prohibition) — ENCODED: `forbid generate(C)` with body `hateful_content(C),
  targets_group(C, G), protected_group(G)`.
* Proposition 1's parenthetical (which groups) — ENCODED: five `protected_attribute` facts +
  `protected_group(G) :- group_defined_by(G, A), protected_attribute(A)`; the "etc." — ENCODED via
  `protected_group(G) :- additional_protected_group(G)`.
* Proposition 2 (the inclusion) — ENCODED as four `hateful_content(C)` rules, one per listed kind,
  with "demeans or dehumanizes" split into two.
* **Deliberately NOT encoded:** (i) sentence 2 as independent prohibitions — see (a), it would forbid
  slurs and insults with no protected-group target, wider than the span; (ii) any `forbid_body` entry
  — see Turn 3/N6; (iii) `root_authority/1` in any body — using it would condition the prohibition on
  a fact about the *section's* authority level, which would make the prohibition fire only where that
  document-side fact is supplied, i.e. weaken it (P5's ⚠️). It is recorded in `requires` with its
  gloss and left unused, exactly as the worked example's third case prescribes.

**Things I could not settle:**

1. **`hateful_content/1` and `protected_group/1` are each BOTH headed in `ontology` and listed in
   `inputs`.** This is intentional — the ontology rules carry the span's stated sub-kinds, and the
   input listing carries the residue that "includes" and "etc." leave open — and it draws no schema
   error and no check note. But it is a shape neither the prompt nor the worked examples exhibit, and
   I could not confirm from the prompt whether the situation-generation stage is happy with a
   predicate that is both derivable and suppliable. If it is not, the correct repair is to rename the
   input leg (e.g. `hateful_toward_group/1`) and add one more inclusion rule — **not** to delete the
   input leg, which would silently narrow the prohibition to exactly four sub-kinds and five
   characteristics.
2. **`additional_protected_group/1` is arguably redundant** now that `protected_group/1` is itself an
   input. I kept both because they carry different provenance: the ontology route makes the "etc."
   inference visible and licensed, while a bare input assertion would not. I chose redundancy over
   losing the licensed inference, but I am not certain that is the house preference.
3. **`closure: unclear` for `generate`.** I am reasonably confident (see Turn 4/N7), but this is the
   single most consequential unforced choice in the module — `cepa` here would have this clause help
   commit the corpus to permitting every other kind of generation, and the failure-mode list says the
   contradiction verdict flips on exactly this. Flagging it as the item most worth a second reader.

**Where I suspect the tooling rather than myself:**
`_debug_gen11/opus_pairs/slice3/validate.py` is **broken against the current API** and cannot be run
as instructed. `schema.validate_all` returns a 2-tuple `(module, breaches)`, and the script iterates
that tuple as if it were a list of errors — so a perfectly clean module is reported as
`schema.validate_all: 2 error(s)` and prints the whole module object as "error 1" and `[]` as
"error 2". Then `checks.run_checks` returns a `CheckResult` dataclass, and the script does
`for n in notes:`, which raises `TypeError: 'CheckResult' object is not iterable` and takes the run
down with exit code 1. I did not edit it (it is outside what I was asked to change, and a coordinator
may be depending on its current text); instead I ran the identical checks from a scratchpad script
that unpacks the tuple and reads `res.findings`. **A translator following the instructions literally
would see "2 schema errors" on a clean module and a traceback, and would very plausibly start
distorting a correct module to chase errors that are not there.** This is worth fixing before the
next wave.
