## 1. QUESTION ZERO — SHOULD THIS CLAUSE HAVE BEEN TRANSLATED AT ALL?

**Answer: YES. Translating it was correct, and abstaining would have been the error.**
This is not a close call, and it is not my taste — the prompt contract decides it explicitly and
in the affirmative, for this exact shape of node.

### (a) Does `00_task.md`'s "it is a section heading" trigger settle this?

No. Another prompt file overrides it, on the record, naming this case.

`00_task.md` says:

> If you cannot translate this clause faithfully — **it is a section heading**, it states a goal
> rather than a condition, it is an example, or its content is not expressible as rules —
> **abstain and give the reason**.

`resolve_runs/graph_v2/node_worked_example.md` contains a section titled *"A heading-authority
node — a structural fact is translatable"*, built on node `l3995_4164_n001`, which is the same
construction as this span (a heading whose attribute block assigns an authority level to its
section). It says:

> **This node obliges nobody, and it is still a translation, not an abstention.** There are three
> routes: a node stating a norm goes to `asserts`; a node stating a **structural fact** about the
> document — which authority a section carries, what class a thing falls in — goes to `ontology`
> with `asserts` empty; only a node that establishes *neither* is an abstention.

and, in bad example 4:

> Pick, on the three-way route: […] "It states no obligation" is not on its own grounds to
> abstain — **the heading node above states none and is translated.**

and in the closing paragraph of the good examples:

> Many graph nodes are commentary, **headings**, or document examples. […] **What decides between
> them is whether the node establishes anything the document says — not what KIND of passage it
> is.**

**Which file wins, and why: `node_worked_example.md` wins, on specificity, not on file order.**
Two grounds:

1. `00_task.md`'s trigger list is subordinated to a condition — "**If you cannot translate this
   clause faithfully** — it is a section heading, …". The list enumerates *typical* reasons a
   faithful translation is impossible; it is not a standalone syntactic test on the span's
   typography. Here a faithful translation is plainly possible, because the source text carries a
   machine-readable authority stamp (`authority=root`) that is a proposition, not a title.
2. `node_worked_example.md` is written for the node input shape (`ESTABLISHES` / `PROVIDES` /
   `NEEDS`), which `00_task.md` predates and does not mention. It addresses this exact
   sub-case — a `####` heading carrying an authority attribute — by name and rules it translatable.
   The specific instruction governs the general one.

Note the asymmetry that makes this the *safe* reading as well as the contract reading: the third
of `00_task.md`'s triggers ("it is an example") was the one that fired unasked on the earlier
clause, and *that* clause established nothing. This one establishes something the document
literally writes down.

### (b) Is `asserts: []` an abstention wearing a translation's label?

**No — it is a legitimate outcome, and the contract states so twice.**

- `node_worked_example.md`: *"a node stating a **structural fact** about the document […] goes to
  `ontology` with `asserts` empty"*, and *"An empty `asserts` list is not an empty module."*
- `10_output_format.md` reinforces the shape from the other side: *"A clause governing no acts —
  a pure definition — needs no closure entry."* The format anticipates modules with no acts and
  no asserts and does not treat them as degenerate.

The discriminating test is not "is `asserts` empty" but "is **every** list empty". An abstention
must be totally empty (`10_output_format.md`: *"leave every list empty. An abstention with content
in it is neither an abstention nor a translation, and is rejected"*; bad example 4 repeats it).
This module has 2 `ontology` entries, 4 `concepts`, 2 `claims`, a `requires` and an `inputs`. It
is content-bearing and it is on the middle route. `asserts: []` here is correct, not a tell.

### (c) `PROVIDES: root_authority` — the consequence for borrowing nodes, and whether it counts

Factually: other graph nodes that `require` `root_authority/N` would, on an abstention, be left
with a body that can never be satisfied. That is failure mode **#15** in `30_failure_modes.md`
("never fired" has three causes, one of which is "waiting on a clause not yet linked in") and
**#3** ("rules that can never fire […] looks like it enforces something and enforces nothing").
The `requires-unprovided` note would fire forever and every downstream authority-conflict query
touching this section would silently resolve as though the section carried no root stamp.

**Does that consequence bear on the right answer, and should it?** Here I want to separate two
things the dispatch is right to be suspicious of.

- "Abstaining would be inconvenient for the graph" is a reason **about the pipeline**, and on its
  own it is an illegitimate reason to translate. If this span established nothing, the correct
  output is an abstention and the stranded borrowers are the *finding* — the pipeline's problem to
  fix by re-segmenting, not the translator's problem to fix by manufacturing content. The
  worked example already draws this exact line elsewhere, in the `inputs`/`requires` warning:
  *"This is not a licence to move a borrowed name into `inputs` to make a module look clean. […]
  a genuine `NEEDS` name whose provider is missing stays in `requires`, and the missing link is
  the finding."* Convenience never licenses content.

- But the reason to translate **this** span is not that one. It is a reason about the DOCUMENT:
  the source text contains `{#avoid_extremist_content authority=root}`. The document itself, in
  its own markup, asserts an authority level for this section. That is a proposition with a truth
  value, present in the narrowed span as a substring (N10 satisfied), and the module records it
  and nothing else. `PROVIDES` is corroborating evidence that the graph read the same proposition
  out of the same text — it is not the ground.

The worked example does invoke the graph-consequence argument (*"other nodes are waiting on this
module […] abstaining would strand every one of them"*), but it is careful to invoke it **second**,
after establishing the structural-fact route, and explicitly notes *"Here the third route is not
available anyway"*. I read that ordering as deliberate and I follow it: the document ground is
sufficient and the graph ground is not load-bearing. **See PROMPT FINDINGS — this is the one place
in the contract where a pipeline-convenience argument is written into teaching material, and it is
one paraphrase away from licensing exactly the fabrication the fence is meant to stop.**

## 2. FINDINGS

### F1 — `root_authority/1` is polymorphic: heading in one entry, rule in the other. **CONCLUSION-CHANGING (in the gloss layer). Fixed by widening the gloss; both ontology entries kept.**

The two entries are:

```
root_authority(avoid_extremist_content_heading).
root_authority(R) :- rule_under_heading(R, avoid_extremist_content_heading).
```

A heading is not a rule, so the predicate's argument type is a union. I considered three verdicts.

**Not a defect to be cured by deletion.** The `TRAP` is real and REVIEW_LIST **N1** names this
case verbatim as the reserved one: *"Reserve ground atoms for facts about the DOCUMENT
(`root_authority(section_x)`), where there is no situation to match."* The ground atom is also
directly anchored: `ESTABLISHES` opens *"The #avoid_extremist_content heading carries root
authority"*, and the span stamps `authority=root` on the heading itself. Deleting it would delete
a proposition the document states in its own markup. **I did not delete it, and a later critic
should not either.**

**Not harmless either.** The defect is not in the two atoms; it is that the module's own `concepts`
gloss for `root_authority` denied one of them. It read:

> "the **instruction** carries root-level authority: the highest level of the chain of command,
> which no system, developer or user instruction can override"

— a gloss whose extension is instructions only, while the module's compiled program puts a heading
constant in that extension. `10_output_format.md` makes the gloss, not the name, the linking
surface: *"the only way another clause's definition can ever be matched to your need is by
comparing what each one SAYS"*, and *"the read-back renders the **definition, not the label**"*.
A borrower matching on that gloss is told the predicate ranges over instructions and will never
learn a heading is in it — the mislink the dispatch asks about is real, and it lands in the
description layer, not the atom layer. This is the same repair shape N8 prescribes for argument
order: make a disagreement surface as a description disagreement rather than silently.

Compounding it: the node's own `PROVIDES` gloss says *"The authority level of **instructions** in
the #avoid_extremist_content section"* while its `ESTABLISHES` says *"The **heading** carries root
authority"*. The node contract is itself in tension about the argument type. The drafter tracked
`PROVIDES` in the gloss and `ESTABLISHES` in the atoms, which is how the seam opened.

**Fix applied — one edit, additive, deletes nothing:** the `root_authority` gloss now reads
*"the argument -- either a rule of the document, or a heading whose attribute block stamps its
section -- carries root-level authority: …"*. Both ontology entries untouched, both claims
untouched, arity unchanged, `PROVIDES` name unchanged. Revalidated: `0 breach(es)`, `errors=0`.

### F2 — `licence: "textual"` on the bodied propagation rule. **Not changed — the prompt licenses it. See PROMPT FINDINGS.**

**PF3 — `prompt/00_task.md` §"Abstention is a real answer" lists "it is a section heading" as an

## 5. CLASSES RAISED

Each is a question a later reader can apply mechanically to a different clause.

**K1 — Type-consistency of a `PROVIDES` predicate's arguments.** *For each predicate this module
defines, do all its `ontology` entries put the same KIND of thing in each argument position, and
does the `concepts` gloss's stated extension cover every one of them?*
**MECHANICALLY CHECKABLE — partly.** Python can flag any predicate with both a ground-constant
entry and a variable-headed entry (a reliable polymorphism trigger, ~5 lines). Deciding whether
the gloss covers both kinds needs a reader. Recommended sweep: flag, don't auto-fix — the fix is
always to widen the gloss, never to delete an entry (N1).

**K2 — `ESTABLISHES` vs `PROVIDES` type disagreement inside the node contract.** *Does
`ESTABLISHES` predicate the provided name of one kind of thing (a heading, a section, the
document) while the `PROVIDES` gloss predicates it of another (an instruction, a rule, a
response)?* This is N3 (diff `ESTABLISHES` against the span) turned sideways — diff `ESTABLISHES`
against `PROVIDES`. **MECHANICALLY CHECKABLE — as a flag only:** grep both strings for the head
nouns and report disagreement for human read. Where it fires, the translator must not silently
pick one; the module should cover both and say so in the gloss.

**K3 — Abstention-trigger accounting.** *If the span matches any of `00_task.md`'s four abstention
triggers on its face (`####`/`###` heading line, a `**Example**:`/`**Bad**`/`**Good**` marker, a
goal-shaped verb), did the transcript consider abstention at all, and did the module state a
ground for translating anyway?* **MECHANICALLY CHECKABLE — yes, cheaply and at high value:** regex
the span for the trigger shapes, and require that a triggered clause's record contain a positive
route statement. This is the exact hole the dispatch reports (zero occurrences of "abstain" in a
triggered clause's transcript). Should be a gate, not a review question.

**K4 — Ground-atom protection.** *Is a ground `ontology` atom about the DOCUMENT (a section,
heading, or policy name as argument), rather than about a situation?* If yes it is N1-reserved and
**must not** be converted to a bodied rule or deleted. **MECHANICALLY CHECKABLE — yes:** flag
ground atoms whose constant argument is also declared as an arity-0 `concepts` entry glossed as a
document part, and mark them protected from any "fix". This is a guard against a *critic*, not
against a drafter.

**K5 — Argument-order pinning on every borrowed arity≥2 relation.** *Does the `concepts` gloss for
each `requires` entry of arity ≥ 2 contain an explicit order statement ("the first … the second",
"X outranks Y")?* (= N8, restated as a checkable property.) **MECHANICALLY CHECKABLE — yes:**
for each `requires` name of arity ≥ 2, test its gloss against an ordinal-phrase pattern; a gloss
with none is a finding. Note the worked example's own `authority_levels_hierarchy` gloss FAILS
this check, so the sweep will hit the teaching material first.

**K6 — `NEEDS`-block routing of every name.** *Is every `requires` entry a name from the `NEEDS`
block, and is every name in the `NEEDS` block in `requires`, and is `requires` ∩ `inputs` empty?*
**MECHANICALLY CHECKABLE — yes, fully, and it should be a hard gate**, since the failure ("a body
that waits forever", #3/#15) is silent and the discriminator is a literal string list in the
prompt. The complementary half — a coined name wrongly placed in `requires` — is what makes the
`requires-unprovided` note uninformative today.

**K7 — Sibling-content leakage from a heading's own text.** *When the span is a heading whose text
is itself an imperative, does the module encode that imperative as an `asserts` entry?* If yes it
has folded a sibling node's content in (`00_task.md`: "you never fold another clause's content
into this one") and will double-encode once the sibling lands. **MECHANICALLY CHECKABLE — yes:**
for a span matching `^#+ ` with a non-empty `asserts`, flag for read. Low false-positive rate,
since a heading node's honest output is `asserts: []`.

## 6. WHAT I COULD NOT SETTLE

1. **PF1, the licence on the propagation rule.** I am not confident `textual` is *right*; I am
   confident it is what the contract teaches, and that changing one module against the worked
   example would make this module an outlier among every other heading-authority node without
   fixing anything. Needs an owner ruling on the prompt, then a cohort-wide sweep, not a
   single-module edit. Recorded, not acted on.

2. **Whether the `root_authority` ground atom is what a borrower actually wants.** I kept it (N1
   protects it, `ESTABLISHES` demands it) and widened the gloss so the union type is visible. But
   whether a downstream authority-conflict query is served by having the heading constant in the
   extension, or merely tolerates it, cannot be answered from inside one clause — I was shown no
   query side and no borrower module, and the fence correctly forbids me from going to look. If a
   linking stage finds the heading constant causes a spurious match, the remedy is a separate
   predicate for the heading (`heading_authority/2`), which is a **graph-level** decision affecting
   the `PROVIDES` name and must not be taken here.

3. **Whether `ESTABLISHES`'s "applying to all rules in that section" is one claim or two.** The
   module reads it as two (C1 heading, C2 rules) and I let that stand — under the one-claim reading
   the ground atom is a literalization rather than a separate proposition, but nothing turns on it
   downstream and collapsing the two would be a content deletion for a stylistic gain. Not worth
   an edit either way; noted so a later reader knows it was considered and declined.
