# PROMPT DEFECT — l1108_1367_n005

> Filed under the brief's stage-5b instruction. **This is not "the module is clean".** It is a
> conflict inside the production prompt that forces the translator to choose which of two
> normative instructions to disobey, and the module records which one I chose.

## The defect

**The production prompt instructs the translator to attach a `textual` licence, citing this
node, to a `concepts` gloss whose content the node's narrowed span does not contain — which the
same prompt elsewhere calls the single worst failure available.**

### The two instructions, by file and line

**A. `prompt/00_task.md`, line 26** (and the licence table above it, lines 20–24):

> **Do not manufacture a citation to make a fact look textual.** Citing a plausible-looking
> clause for something the clause does not actually say is the single worst failure available
> here: it creates an invented entity *behind a passed check* … An honest `assumed` is always
> better than a dressed-up `textual`.

with the table defining `textual` as *"the cited clause says this"*.

**B. `resolve_runs/graph_v2/node_worked_example.md`, lines 47–49** — the good worked example's
borrowed-gloss entry:

```json
{ "name": "authority_levels_hierarchy", "arity": 2,
  "gloss": "which of two levels of the chain of command is the higher one",
  "licence": "textual", "cites": "l527_796_n012", "inference": null, "toggleable": false }
```

`authority_levels_hierarchy` is a **NEEDS** name: the example's own header (line 27) says
another node establishes it, and its narrowed source text (L0618, *"These implicit biases are
subtle and serve as defaults only — they must never override explicit or implicit instructions
provided by higher levels of the chain of command"*) does **not** state which of two levels is
higher, or that levels are ordered at all. So the example marks `textual` and cites the node for
a gloss the cited text does not supply.

Reinforced by **`node_worked_example.md` line 19** (*"Give it a `concepts` entry carrying the
meaning the node text hands you"*) and **line 133** (*"each also has a `concepts` entry
restating the meaning the node handed you"*) — both correct about **content**, neither saying
anything about **licence**, so the example's JSON is the only signal a translator has, and it
says `textual`.

`prompt/10_output_format.md` line 66 is what makes this unavoidable rather than optional: *"every
`requires` entry must **also** have a `concepts` entry saying what you need it to MEAN."* Every
node with a non-empty NEEDS block hits this fork.

### Why it is a defect and not a distinction I have missed

The two cannot be reconciled by reading `textual` as "the *graph* says this", because the
schema's own field description fixes the referent: `cites` is *"clause id — REQUIRED and
non-empty when textual"*, and `00_task.md`'s table glosses `textual` as *"the cited clause says
this"*. There is one citable id per module (the node's own), so a `textual` NEEDS gloss can only
be a claim about the narrowed span.

## What I did, and what it cost

I followed **A** and departed from **B**: `root_authority/1` carries

```
"licence": "assumed", "cites": null,
"inference": "the node's NEEDS block hands this concept in with that meaning; the narrowed
              span itself says nothing about any authority level, so the gloss is taken from
              the graph and not from the cited text"
```

The narrowed span of this node — *"If a user shows signs of vulnerability to radicalization…"* —
contains no word about authority, about the `#avoid_extremist_content` section, or about root
level, so `textual` here would be a citation to text that does not support the gloss.

Grounds for preferring A over B, beyond A being the stronger-worded instruction:

* **PROVISIONAL.md, ground 2** already decides the identical question for content arriving from
  `ESTABLISHES` rather than from a `NEEDS` block: *"anything ESTABLISHES adds is still
  expressible: as `assumed`, with the inference naming ESTABLISHES as its source. Nothing is
  lost, only marked."* A NEEDS gloss is the same species of import from the graph layer.
* **Nothing is lost by A.** Contract 2 is fully satisfied — the name is in `requires` spelled
  exactly, with a `concepts` gloss carrying the node's meaning. The cross-module link is made by
  the **gloss prose**, which `10_output_format.md` lines 65–71 say explicitly is the linking
  mechanism; the `licence` field plays no part in it.
* **The costs are asymmetric.** A wrongly-`assumed` gloss under-claims and stays visible and
  reviewable. A wrongly-`textual` gloss is an invented entity behind a passed check, and
  `validate.py` reports it clean either way — I confirmed this: my module returns **0 breaches,
  0 errors** with `assumed`, and would have done so with `textual` too. **No deterministic check
  in this pipeline can tell the two apart**, which is precisely why the prompt's own worked
  example can teach the wrong one indefinitely without anyone noticing.

## Recommended repair (for the prompt owner, not applied by me)

Either

1. **amend `node_worked_example.md` lines 47–49** to mark the NEEDS gloss `assumed` with an
   inference naming the NEEDS block, and add one sentence under the "Things to notice" list
   saying that a NEEDS gloss is content imported from the graph and therefore never `textual`
   unless the narrowed span independently states it; **or**
2. **amend `00_task.md`'s licence table** to say explicitly that a NEEDS gloss may cite the node
   as the *carrier* of the graph's assignment — which would make B correct but weakens the
   meaning of `textual` corpus-wide and should not be done casually.

I recommend (1). It is the narrower change, and it leaves `textual` meaning exactly one thing.

**Until it is repaired, this fork is invisible in every measurement**, because both answers pass
every check the pipeline runs.
