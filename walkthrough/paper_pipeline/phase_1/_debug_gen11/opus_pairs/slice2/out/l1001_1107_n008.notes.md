## UNSURE — things I could not settle

### UNSURE-1 ⭐ — the *should* hedge is not encodable, and I am recording that (P7)

The span says *"should be able to"*, not *"may"*. In this document *should* marks a
**default** — overridable by higher authority — and `status` has no defeasible pole.
P7's remedy is to push the defeater into a body; **there is no defeater in the narrowed
span** to push. N2's remedy (promote the hedge to a predicate) does not apply either:
that remedy is for a hedge that is the *matrix verb* with a rule as its object, and here
*should* is a modal on the norm itself, so promoting it would coin an unanchored symbol
(N10).

What I did instead: chose `permit`, the weakest grant available, so the module does not
overstate the entitlement; kept *"should be able to"* verbatim in the `read_back` so a
reviewer sees the hedge; and wrote it here. **An unconditional `permit` and a `permit`
whose default was dropped are byte-identical, so this paragraph is the only record that
a commitment was made.**

### UNSURE-2 — `ontology` is empty, deliberately

I considered coining `publicly_disclosable_information(I)` bodied by
`generally_public(I), unlikely_to_cause_harm_through_disclosure(I)`, to give the
two-conjunct class a name. I did not, on failure-mode-5 grounds: it would be one symbol
named after the clause's own words sitting between the assert and the two conditions
that already carry all the content, adding a layer without adding a fact. Both conjuncts
go directly into the assert body instead, which is what the third worked example
(`l4251_4571_n029`) does with `ontology: []`. I am not fully certain — a linker might
prefer the named class — so it is recorded rather than settled.

### UNSURE-3 — the arity of `privacy_context_dependence`

The NEEDS gloss (*"whether information is private or sensitive depends in part on
context"*) does not fix an arity. I chose **2** — `(Information, Context)` — over the
1-place reading (*"I's privacy status is context-dependent"*) because 2 keeps the context
visible as a term another node can bind. Per **N8**, the argument order is written into
the `concepts` gloss in words ("first argument the information, second the context") so
that a provider disagreeing with me surfaces as a description mismatch rather than a
silent inversion. If the providing node turns out to be 1-place, that is the finding.

### UNSURE-4 — `information_about/2` is an addition, marked `assumed`

*"For public figures, the assistant should be able to provide information…"* does not
literally say the information is **about** the public figure. I read it that way (the
sentence sits under *"private or sensitive information **about people**"*, and the
alternative reading — any information at all, provided a public figure is in the
conversation — is not a reading anyone would defend). But the word is not in the
narrowed span, so it is `assumed` with the inference named, never `textual`. It is also
load-bearing formally: without it `P` is unbound in the assert body.

### UNSURE-5 — closure `unclear` vs `cnpa`

I chose `unclear` for `provide_information`. The case for `cnpa` is real — a permission
carve-out is pointless unless something outside it is prohibited, and the un-narrowed
sentence before this one *is* that prohibition. I rejected it because that prohibition is
**outside the narrowing** (P6), so asserting `cnpa` would import it. `cepa` was rejected
on N7's reasoning: it re-asserts a silence this clause declines to settle. `unclear` is
the reading that leaves the un-narrowed prohibition to the node that owns it.
