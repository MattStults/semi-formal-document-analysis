# UNSURE — everything I could not settle

### UNSURE 1 ⭐ (the important one) — `root_authority` is in BOTH `PROVIDES` and `NEEDS`, and the two contracts contradict each other

The node lists `root_authority` in `PROVIDES` (*"use EXACTLY these names as the
predicates **this module defines**"*) **and** in `NEEDS` (*"established by OTHER nodes …
belongs in this module's `requires` … **never in `ontology`, never defined here**"*).
These cannot both be honoured. This is a self-loop in the graph — a node that needs what
it provides — and I read it as a defect in the node's contract, not as a choice the span
leaves open.

**I resolved it in favour of `PROVIDES`:** `root_authority/1` is defined in this
module's `ontology`, and `requires` is empty. Grounds:

1. **The span supports it.** `authority=root` is *in this node's own narrowed text*. If
   any node in the corpus owns the fact that the #respect_creators section carries root
   authority, it is this one. Routing it to `requires` would say another node states
   what this node's own verbatim text states.
2. **The worked example's heading-authority node is the same shape and goes this way**
   — `PROVIDES: guideline_authority`, defined in `ontology`, with the instruction *"do
   deliver what `PROVIDES` promises"* and the warning that abstaining/deferring
   "would strand every one of them".
3. **The failure directions are asymmetric.** Defining it here and being wrong produces
   a duplicate definition, which surfaces at link time as a visible disagreement.
   Putting it in `requires` and being wrong produces a module that defines nothing, has
   an empty `ontology`, waits forever on a definition no node supplies, and silently
   strands every dependent — failure mode #15's third cause, which is the one that
   cannot be told apart from a dead rule.

**What would change my mind:** a coordinator ruling that `NEEDS` wins on collision, or
evidence that a *different* node in the corpus also provides `root_authority` from the
authority-hierarchy section (in which case the two definitions must be reconciled, and
mine is the section-membership half). I cannot check either from inside my fence. **This
is the single most consequential unresolved decision in the module and it should be
looked at directly.**

### UNSURE 2 — is the ontology entry's licence right at `assumed`?
I moved it `textual` → `assumed` under N3 (turn 1), because the scoping from *heading*
to *rules under the heading* is markup convention rather than stated text. The parallel
worked example marks its structurally identical entry `textual` — but its source text was
not shown, so I could not tell whether its span stated the scoping and mine does not. If
the ruling is that an authority attribute on a section heading *just is* a textual
statement about the section's rules, this should revert to `textual` and the inference
string be dropped. I chose the direction `00_task.md` names as always-safer (an honest
`assumed` over a dressed-up `textual`), but I am not certain, and it is a divergence from
the worked example's visible shape that a reviewer should see rather than discover.

### UNSURE 3 — arity and argument sort of `root_authority/1`
I made it range over **rules** (`root_authority(R)`, R a rule), on both graph glosses,
which say *"**rules** in the #respect_creators section carry root authority"*. An
alternative reading makes it range over **sections** (`root_authority(section)`), which
is what N1 offers as its own example of a legitimate document-level ground atom. A
consumer node that expects the section reading will fail to link against mine, and the
mismatch will look like a missing provider rather than a sort disagreement. The gloss is
written to make the disagreement surface as a description conflict (N8's remedy applied
to a provided rather than a borrowed name), but I cannot verify the consumers' reading
from inside the fence.

### UNSURE 4 — `defines` left empty
I considered `defines(l1001_1107_n001, root_authority, respect_creators_heading)`, since
this node does fix which rules fall under a class. **Left empty:** `defines` fixes the
extension of a class over a *term*, and the class here extends over rules, not over the
heading — the entry would read "the class root_authority covers the heading", which is
not what the node says. The worked example's heading node also leaves `defines` empty and
uses `ontology`. Low confidence that this is worth a second look, but recorded.
