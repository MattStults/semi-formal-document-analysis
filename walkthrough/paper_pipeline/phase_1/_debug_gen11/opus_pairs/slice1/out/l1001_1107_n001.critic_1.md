## ⭐ Q1 — THE FRAME: should this clause have been translated at all?

**Yes — but not because it states a norm. It states a STRUCTURAL FACT about the document,
and that is the second of the three routes.**

The narrowed span is exactly one line and it is a section heading:

> `#### Respect creators and their rights {#respect_creators authority=root}`

Taken as a norm, this clause should have abstained: it obliges nobody, permits nothing,
forbids nothing, and there is no act in it. The module agrees — `asserts` is empty, `acts`
is empty, `closure` is empty. That is the correct reading.

But a heading is not automatically an abstention, and `node_worked_example.md` settles this
case by name. Its second worked example, `l3995_4164_n001`, is *the same shape*: a heading
node whose only content is that the rules under it carry an authority level. The file says
(lines 155-158):

> "**This node obliges nobody, and it is still a translation, not an abstention.** There are
> three routes: a node stating a norm goes to `asserts`; a node stating a **structural
> fact** about the document — which authority a section carries, what class a thing falls
> in — goes to `ontology` with `asserts` empty; only a node that establishes *neither* is an
> abstention."

Two things state the norm-free content that makes this route available:

1. the words `authority=root` in the span — a literal attribute the document writes on this
   heading, which is a fact about the document;
2. the `PROVIDES` block, which names `root_authority` — other nodes are waiting on this
   module to make that predicate derivable. Same file, lines 159-162: abstaining here
   "would strand every one of them."

So the frame answer is **translate, with `asserts` empty** — which is what the module did.
It is not the heading-ness that would license abstention (bad example 4: *"'It states no
obligation' is not on its own grounds to abstain"*); it is establishing nothing at all, and
this node establishes something.

I also checked the abstention direction is not the right one on a technicality — the span
is not `**Example**:`-headed, is not a goal statement, and the content *is* expressible: one
bodied ontology rule expresses it, and the module wrote exactly that one.

## Q2 — findings

### F1 — `root_authority` appears in BOTH `PROVIDES` and `NEEDS`; the module honoured PROVIDES and left `requires` empty — **NOT A DEFECT** (translator), but see PROMPT FINDING

This is the sharpest thing in the module and it is where I expected the defect to be.

`node_worked_example.md` contract 2 (lines 16-19) is stated without exception:

> "**Every `NEEDS` name goes in `requires`, spelled exactly as given** … Never define a
> `NEEDS` name in your `ontology` — another node owns it."

and the third worked example reinforces that it is not conditional on usefulness (line 268):
*"The `NEEDS` name went to `requires` even though the module never uses it."* `REVIEW_LIST`
P9's correction says the same in bold: *"A `NEEDS` name in `requires` and unused is
CONTRACT-REQUIRED and must be left alone."*

Read mechanically, that says `requires: ["root_authority/1"]`. But this node's `NEEDS` name
**is its own `PROVIDES` name**. Obeying contract 2 here would require the module to
simultaneously (a) list `root_authority/1` in `requires`, i.e. declare that *another* node
owns it, and (b) define `root_authority(R)` in `ontology`, which the same sentence of the
same contract forbids — while `PROVIDES` orders (b) in capitals ("use EXACTLY these names as
the predicates this module defines"). The two contracts of this node contradict each other,
and no module can satisfy both.

The module picked `PROVIDES`. I judge that the correct pick, for three reasons: the
`PROVIDES` instruction is the one that has downstream consumers waiting; the worked example
of exactly this node shape (`l3995_4164_n001`) writes `requires: []` and defines the
authority predicate in `ontology`; and a `requires` entry for a name you also define is the
worse artifact — it tells the linker to go looking for an owner that is this very module,
which is failure mode 15 ("waiting on a clause not yet linked in") manufactured from
nothing.

Cost of the choice, stated for the record: the graph edge that put `root_authority` in
`NEEDS` is now invisible in the module. That is a real loss of inspectability, but it is a
loss caused by the node contract, not by the translator, and the alternative loses more.
**Not a translator defect.** Filed below.

## PROMPT FINDING

### PF1 — contract 2 is unsatisfiable on a node whose `PROVIDES` name is also its `NEEDS` name

`node_worked_example.md`, lines 16-19:

> "2. **Every `NEEDS` name goes in `requires`, spelled exactly as given** (you choose the
> arity: `authority_levels_hierarchy` becomes `authority_levels_hierarchy/2`). **Never
> define a `NEEDS` name in your `ontology`** — another node owns it."

and the span, lines 15-20, hands the translator both:

> `PROVIDES … - root_authority: rules in the #respect_creators section carry root authority`
> `NEEDS … - root_authority: the authority level of rules in the #respect_creators section`

These cannot both be obeyed. The contract as written admits no tie-break, and `REVIEW_LIST`
P9's correction hardens the `NEEDS` side ("must be left alone"), which means a future critic
following P9 mechanically will charge this module for an empty `requires` and be wrong — the
same class of error P9 itself was corrected for (an entry that fires on correct work).

This is not the translator's defect and the module should not be marked down for it. The
prompt needs one added sentence: **when a name appears in both `PROVIDES` and `NEEDS`, the
node owns it — define it in `ontology` and omit it from `requires`.** Whether the graph
should be emitting self-`NEEDS` edges at all is a separate question for the graph stage.

**I decline any fix that would add `root_authority/1` to `requires` on contract-2 grounds,
and this is the reason.** Per the brief: a clean module and a prompt defect are two different
verdicts. This module is clean; the node contract is defective.

### PF2 — the worked example teaches `textual` for a scoping inference that is genuinely `assumed`

`node_worked_example.md`, line 201:

> `{ "atom": "guideline_authority(R)", "body": "rule_under_heading(R, unprompted_personal_comments_heading)", … "licence": "textual", "cites": "l3995_4164_n001", "inference": null, … }`

The step from "the heading is marked with an authority" to "every rule under the heading

Low severity, but it is a template that every heading-authority node in the corpus will be
drafted against, so the divergence propagates. **The module is right and the example is
wrong**, and I record it here rather than charging the module.
