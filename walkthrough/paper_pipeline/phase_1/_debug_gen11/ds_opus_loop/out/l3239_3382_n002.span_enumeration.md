## The structural traps I expect, stated in advance

* **T1 — `PROVIDES` names `avoid_overstepping`, and its gloss calls it a
  SECTION**: *"The policy **section** on avoiding overstepping, referenced by
  the imminent harm rule."* The module MUST define that exact name. The span's
  content is a behaviour rule about helping; the provided name is a
  section identity. Predicted defect: either the name is never defined at all,
  or it is defined as "the response does not overstep", which is not what the
  consumer (the imminent harm rule) is told it will get.
* **T2 — the narrowing removes the only thing the provided name is about.**
  `ESTABLISHES` says *"without overstepping"*; the narrowing does not. A draft
  that follows the narrowing drops S7; a draft that follows `ESTABLISHES` keeps
  it. Both are defensible; **silence about the conflict is not.**
* **T3 — `letter_and_spirit` is a cross-reference, not a NEEDS name.** It must
  not appear in `requires`. Coining it is the invented-name class.
* **T4 — NEEDS is exactly `assistant_definition` and `user_authority`.** Both
  belong in `requires`, spelled exactly, never in `ontology`, never in
  `inputs`. Per the production prompt's contract 2 they may correctly be
  UNUSED.
* **T5 — `user_authority`'s gloss here is *"Rules in the #avoid_overstepping
  section carry user-level instruction authority."* That is a statement about
  authority LEVEL of a section's rules. A gloss rewritten to be about a user's
  request is failure mode #9.
* **T6 — collapsing S4.** `help(developer)` and `help(user)` are two, or one
  predicate over a party variable. Encoding only "the user" drops half the
  span.
* **T7 — collapsing S3 into S5.** Obliging `follow_explicit_instructions` and
  `address_implied_intent` while never encoding *helping* changes the head of
  the rule; whether that matters is a judgement I will make against the draft,
