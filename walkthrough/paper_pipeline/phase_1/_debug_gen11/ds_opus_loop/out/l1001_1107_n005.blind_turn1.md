## Findings

### ⭐ F1 — the module's one rule is licensed `textual` on a step the span does not state. FRESH. **This is the pre-registered T3 defect and it fired.**

```json
{ "atom": "root_authority(R)",
  "body": "rule_under_heading(R, protect_privacy_heading)",
  "licence": "textual", "cites": "l1001_1107_n005" }
```

`textual` means *"the cited clause says this"*. The cited clause is, in its
entirety:

> `#### Protect people's privacy {#protect_privacy authority=root}`

That string states that a **heading** carries the attribute `authority=root`.
It does **not** state that every rule underneath the heading carries root
authority. The step from the one to the other is the document's **structural
convention** — that a heading's attribute scopes over the section beneath it —
and **that convention appears nowhere in the span.** `00_task.md`: manufacturing
a citation is *"the single worst failure available here"*.

⚠️ **The asymmetry inside the draft is the evidence.** The draft licensed
`rule_under_heading/2` **`assumed`**, with the inference spelled out (*"the node
speaks of every rule under the heading, so a relation between a rule and a
heading must exist"*). It knew the relation was inferred — and then licensed the
rule built out of it `textual`. One `concepts` entry apart. Same shape as clause
5's F2.

⚠️ **`ESTABLISHES` says it with a *"so"*:** *"The heading … carries root
authority, **so** every rule under it is a root-level rule."* The node's own
wording marks the step as an inference, and the module erased the marking.

**Severity: DECISIVE for what the module claims to rest on.** The conclusion is
probably right; the *record of why it is believed* is false, and #16 is the
failure mode that says a reviewer cannot see through a `textual`.

**Remedy:** licence `assumed`, `cites` null, `inference` naming the scoping step.

### F2 — `root_authority/1` is in `requires` **and** defined by this module's `ontology`. FRESH.

`requires` = *"predicates this module uses that **another clause** must
define"* (rule 9). No other clause must define `root_authority` — **this module
defines it**, in the same object, as the head of its only rule. The `requires`
entry is a false statement of provenance, and failure mode #15 is exactly about
that (*"declare `requires` honestly so [waiting-on-an-unlinked-clause] can be
told from [genuinely dead]"*).

⛔ **This is the node's own contradiction, and my pre-registration did not
anticipate the draft taking BOTH horns.** Recorded as an error in my
pre-registration, which said I would score only a draft that *dropped* the name
or *hid* the conflict. Doing both is a third thing, and it is the one that hides
the conflict best: nothing in the module records that a choice was ever forced.

**Which horn wins is decided mechanically, not by preference.** `schema.py:789`
rejects a `translated` module that emits no assertion, definition, superiority
or ontology fact. So the NEEDS horn — `root_authority` in `requires`, defined
nowhere — **cannot produce a `translated` module at all**; it can only produce
an abstention. The PROVIDES horn is the only one that yields a module, and it is
the horn `ESTABLISHES` and eight downstream siblings need.

⚠️ **Evidence the NEEDS listing is a blanket, not a claim:** measured, all
thirteen nodes of `L1001-1107` carry `root_authority` under NEEDS — including
the two heading nodes that PROVIDE it. A per-node NEEDS list would not list a
node's own output.

⚠️ **Against myself:** deleting it leaves `requires` empty and disobeys a
**bold** instruction in the node. That cost is real and is written into the
notes rather than hidden. → **graph-defect recommendation.**

**Severity: MODERATE.** No conclusion changes; the provenance record does.

**Remedy:** delete `root_authority/1` from `requires`, change nothing else about
it. Its `concepts` entry stays — the module still has to say what its own
predicate means.

### F3 — the `root_authority` gloss states a **superiority** the span does not, under a `textual` licence. FRESH.

> *"the rule carries root-level authority: **the highest authority level in the
> Model Spec, overriding lower-level rules**"* — `licence: textual`,
> `cites: l1001_1107_n005`

Neither *"the highest authority level in the Model Spec"* nor *"overriding
lower-level rules"* is anywhere in this node — not in the span, not in
`ESTABLISHES`, not in PROVIDES, not in NEEDS. The node's own words are *"rules in
the #protect_privacy section carry root authority"*.

⚠️ **Why it is worse than a loose gloss: it is a ranking, and rankings have a
field.** Rule 8b: *"A superiority claim goes in `beats`, with this clause as the
sayer."* *"Overriding lower-level rules"* is a superiority claim living in prose,
where nothing formal carries it, nothing can check it and nothing downstream can
use it — failure mode #5's shape.

⛔ **Rejected by name: adding a `beats` entry.** Pre-registered under T8 — this
span **names no loser**, so a `beats` entry would have to invent one. The claim
should be **removed**, not promoted.

⭐ **This is the SECOND independent draft to inflate the same predicate.** Clause
5's F1 recorded a draft expanding a borrowed `root_authority` gloss to *"the
highest level of the chain of command"*. Different section, different node,
different draw, **same manufactured expansion of the same name.** MEASURED, n=2.

**Remedy:** cut the gloss back to what the node says. `textual` then becomes
honest, because the PROVIDES block is literally inside this node's `quote` —
clause 4's ruling, which holds only while the gloss stays close to the node's
words.

### F4 — `protect_privacy_heading` is a **constant**, declared as a 0-ary **predicate**. FRESH. LOW severity, and the counter-argument is recorded.

`concepts` declares `protect_privacy_heading`, `arity: 0`. The module never uses
it as a predicate; it uses it as the **ground second argument** of
`rule_under_heading(R, protect_privacy_heading)`. In the rendered `.lp` a 0-ary
atom and a ground constant of the same spelling are indistinguishable to a
reader, which is failure modes #8/#9 manufactured inside one module.

⛔ **The counter-argument, recorded because it is close to decisive.**
`schema.py` carries a deliberate comment that there is *"no check that a declared
concept is used somewhere in its own module. Introducing vocabulary it does not
itself use is exactly what a definitional clause does."* This **is** a
definitional clause. If the objection were *"the concept is unused"* I would drop
it under that comment. **The objection is that it is mis-typed, not unused** —
and the constant it shadows is the load-bearing artifact.

**Remedy:** delete the `concepts` entry. A ground constant requires no
declaration, and the entry advertises a predicate on the concept table, which the
schema calls *"the only channel that could ever link them."*
