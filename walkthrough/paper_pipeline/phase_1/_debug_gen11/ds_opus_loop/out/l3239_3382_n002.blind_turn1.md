## Findings

**B1 / B2 — the two the floor caught.** `overstep(A)` is asserted but absent
from `acts`; consequently the `closure` entry for `overstep` is "declared for
act class(es) the module does not govern". One root cause: the third act was
never declared.

**F1 — the circular `ontology` rule makes the module's only prohibition
dead. DECISIVE.**
```
atom: "overstepping(A)"
body: "avoid_overstepping(R), user_authority(R), overstepping(A)"
```
The head appears verbatim in its own body. Nothing else derives
`overstepping/1` — it is not in `inputs` — so no instance is ever derivable,
so `forbid overstep(A) :- assistant_definition(A), overstepping(A)` can never
fire. The module *reads* as though it forbids overstepping and formally
forbids nothing. `R` is also unrelated to `A` by any conjunct.

**F2 — `A` is bound to the assistant and to an action in the same body.
DECISIVE.** Third assert: `body: "assistant_definition(A), overstepping(A)"`.
The draft's own glosses type these incompatibly — `assistant_definition`:
*"**A is the entity** the end user or developer interacts with"*;
`overstepping`: *"**A is an action** that goes beyond what the assistant is
authorized to do"*. The rule therefore fires only where the assistant **is** an
overstepping action. The first two asserts use `assistant_definition(A)` with
`A` free and unused elsewhere, which is harmless; here it collides.

**F3 — the graph edge is inverted: this node's PROVIDES name is filed as a
NEEDS name. DECISIVE at the graph level, and no check can see it.**
`requires` is `["assistant_definition/1", "user_authority/1",
"avoid_overstepping/1"]`. The node text says
*"**PROVIDES** (use EXACTLY these names as the predicates **this module
defines**): - avoid_overstepping"*, and NEEDS lists exactly two names with
*"every one of them belongs in this module's `requires`"*. `avoid_overstepping`
is the one name this node is commissioned to **supply**, and the draft declares
it as something another node supplies. Downstream, the imminent-harm rule that
*"references"* it is never satisfied by anybody.
⚠️ **Machine-invisible:** `grep -l provides checks.py link.py fixtures.py`
returns nothing. No check reads the PROVIDES block, so `requires-unprovided`
fires here exactly as it fires on every correct single-clause module, and the
inversion is indistinguishable from the benign case.

**F4 — the read-back asserts a qualifier the rule does not carry.**
read_back: *"the assistant should **reasonably** address implied intent %"*;
the rule is `oblige address_implied_intent(I) :- assistant_definition(A),
implied_intent(I)` — unconditional over every implied intent. The span says
*"**reasonably** addressing implied intent"*. The module concludes something
strictly stronger than the span, and the read-back conceals it by containing
the missing word.

**F5 — S4 dropped: two beneficiaries became none.** The span says *"help **the
developer and user**"*; `ESTABLISHES` repeats it. No predicate in the module
ranges over parties; the distinction survives only inside the
`explicit_instruction` gloss (*"stated explicitly by the developer or user"*)
and in `claims` C1/C2, which say *"help the developer and user"* with no formal
counterpart. Claims/asserts drift on this element.

**F6 — S3 dropped: *helping* is never encoded.** *"should **help** … **by**
following … and … addressing"*. The draft obliges the two MEANS directly and
never the act they are means to. I record this as **noted, not repaired** — the
means-only encoding is defensible and repairing it would require an act term
the module does not have. It is not a defect I would spend a turn on.

**F7 — `cepa` on `follow_instruction` and `address_implied_intent`.** The
reason given (*"silence permits actions not covered by the obligation"*) is a
global permission commitment read off a one-sentence span with no permissive
language anywhere. Lower priority than F1–F4; parked for a later turn.
